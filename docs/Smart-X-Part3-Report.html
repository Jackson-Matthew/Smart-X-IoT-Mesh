1. Summary of the completed project

Smart-X is an IoT operations console made of a .NET 10 Web API and a React and TypeScript dashboard. Part 1 built the ingestion gateway: sensor registration, validated telemetry through a generic TelemetryPacket<T>, file attachments and a jagged-array history. Part 2 added real-time handling: a FIFO queue and a priority queue for alerts, a stack for command undo, dictionaries for O(1) device lookup, a HashSet to stop duplicate alerts, a SortedDictionary timeline and a predictive action engine. Part 3 finishes the system with the Network Topology and Mesh Routing module. It models the sensors as a mesh graph, finds connected and failed nodes with BFS and DFS, calculates the most power-efficient routing tree with Prim's algorithm and a min-heap, and stores timestamped history in AVL trees so that time ranges can be queried without scanning everything. All three modules are now active in the sidebar, and Parts 1 and 2 were left working as they were.

2. Architectural and algorithmic challenges, and how they were solved

2.1 Keeping mesh health independent of the Part 2 disconnect monitor

The first idea was to say a mesh node is "down" when the Part 2 DisconnectMonitor flags it. That monitor marks any device silent for 60 seconds, so any time the Part 1 simulator was not running, every node turned red and a breadth-first search from the gateway reached nothing. The demo became meaningless. I separated the two concerns: the mesh service owns its own failure set (seeded with TEMP-002, the sensor that never reports) and exposes an endpoint and button to fail or restore a node. The gateway itself cannot be failed, because it is the mains-powered link to the server. The mesh was also wired in as new classes (MeshSeedService, MeshTopologyService) so the Part 1 and Part 2 seed code did not have to change.

2.2 What a minimum spanning tree does and does not optimise

The brief asks for the MST to show the most power-efficient route. While testing I compared the tree path of PUMP-002 (77 mW over 7 hops) with its fewest-hops BFS path (53 mW over 4 hops). The MST path was more expensive for that one node. That is not a bug: Prim's algorithm minimises the total cost of the links the whole network keeps awake (127 mW across 12 links, against 272 mW if all 22 working links stayed on), it does not minimise each node's own path. I removed a per-node "power saved" figure I had first added, because it would have been misleading, and instead report the network-wide saving in the summary cards and explain the trade-off in the README. Understanding this difference between an MST and a shortest-path tree (Dijkstra) was the most important algorithmic lesson of Part 3.

2.3 Making the AVL benchmark honest

The page shows how much faster the tree query is than a scan. My first measurement reported 3,287 µs for the AVL tree and 1,020 µs for the linear scan, so the "optimised" structure looked slower. The cause was one-off JIT compilation on the first call, and the scan was also doing less work because it only counted matches instead of building a result list. I changed both paths to build a result, added a warm-up, and averaged 50 runs each. The corrected figures were about 5-7 µs for the tree against about 27-42 µs for the scan on 730 readings. The more reliable metric is the number of tree nodes visited (69 against 732), which does not depend on the machine, so the page shows both.

2.4 Connecting the C# backend to the React frontend

Several integration details needed care. (a) Enums, timestamps and the interface-typed ITelemetryPacket.Data must serialise predictably so TypeScript receives plain objects; the existing JSON options plus a Record<string, unknown> type kept this simple. (b) The datetime-local inputs work in local time while the AVL tree is keyed on UTC, so the page converts through Date to ISO strings and the API normalises with ToUniversalTime(). (c) The AVL index is fed from two places, the seeder and the live ingestion pipeline, so a lock protects each device's tree. (d) The dashboard keeps all pages mounted, so the topology page polls every 8 seconds and refreshes immediately after any action instead of showing stale data. (e) Drawing the graph with a plain SVG, using positions held in the seed data, avoided a heavy graph library and made node clicks, route highlighting and failure colouring straightforward.

2.5 Smaller engineering issues

Cloning the Part 2 project into a deeply nested scratch folder failed on Windows because of the 260-character path limit; enabling core.longpaths and using a short working path fixed it. Duplicate timestamps would have overwritten readings in the tree, so the index nudges a clashing timestamp forward by one tick, as the Part 2 SensorTimeline already did. Finally, I seeded 24 hours of history directly into the trees (about 9,400 readings) so range queries can be demonstrated under load without waiting for live data.

3. Key learnings

AreaWhat I learned, linked to this project
Choosing a structure for the questionEach Smart-X feature came from asking which question the operator asks. "Which readings between 14:00 and 16:00?" is a range query, so a sorted tree. "Which devices are still connected?" is reachability, so a graph traversal. "Cheapest way to link everything?" is an MST. A List would have answered all of them, but slowly or with repeated scanning.
Why balance mattersTelemetry arrives in timestamp order, the worst case for an unbalanced BST. Seeing 721 readings sit in a tree of height 10, with 711 rotations needed to keep it that way, made the AVL rotations concrete.
Heaps and greedy algorithmsWriting the heap by hand (sift up, sift down, parent and child index arithmetic) showed why Prim is O(E log V): the heap removes the "find the cheapest link" scan.
BFS versus DFSBoth find the connected set, but BFS also gives fewest-hop distances, which suits failover reporting, while DFS is simpler to explain as "dive then back up". Having both selectable on the page made the difference visible.
Measuring honestlyThe benchmark mistake in 2.3 taught me to warm up, average, and also report a machine-independent count.
Generics and clean architectureParts 1 and 2 introduced TelemetryPacket<T> and DI singletons. In Part 3 the same pattern made a reusable AvlTree<TKey,TValue> and let the new modules plug into ingestion with a single added line.
IoT domain knowledgeModelling Zigbee, Thread and ESP-NOW style meshes showed why self-healing matters in the field and why links carry a power cost on battery-powered ESP32 nodes.
ProcessWorking in small commits, building and testing each layer (API with curl, then the UI in a browser) before moving on caught the benchmark and MST-comparison problems early.

4. Technology recommendations

The current system runs in memory with simulated devices. These additions would take it towards a production deployment, and all of them fit the existing .NET 10 and React stack.

TechnologyBenefit for Smart-XWhy it suits this project
MQTT broker (Mosquitto or EMQX, with the MQTTnet client)Real ESP32 devices publish telemetry over a lightweight publish/subscribe protocol, replacing simulated HTTP posts.MQTTnet is a .NET library; a hosted BackgroundService can subscribe and pass messages into the existing TelemetryService pipeline unchanged.
Time-series database (TimescaleDB on PostgreSQL, InfluxDB, or Azure Data Explorer)Persistent history that survives restarts, with built-in time-range queries, retention and downsampling. The in-memory AVL trees would remain as a hot cache for recent data.EF Core and Npgsql work with TimescaleDB; the ITelemetryRepository interface already isolates storage, so the swap is local.
SignalR (ASP.NET Core)Pushes alerts, node failures and topology changes to the dashboard instantly instead of 8-10 second polling.First-party to ASP.NET Core with an official JavaScript client for React.
GitHub Actions CI/CDBuilds the API and dashboard, runs tests and builds Docker images on every push, catching compile errors before submission or deployment.The repository already uses GitHub and Docker; the official setup-dotnet and setup-node actions cover both halves.
Automated tests (xUnit and Vitest)Tests for the AVL balance, range query, BFS/DFS and Prim results would protect the algorithms against regressions. The project currently relies on manual and API testing.xUnit is the standard .NET test framework, and the structures are pure classes with no dependencies, so they are easy to test.
Home Assistant integrationLets Smart-X devices appear in a home or building automation hub and use its dashboards and automations.Home Assistant accepts MQTT discovery messages, so it builds on the MQTT recommendation above.
LLM API summaries (for example the Claude API)Turns a day of alerts and failovers into a plain-language summary for operators and suggests likely causes.Called through the .NET HttpClient from a scheduled background service; only aggregated alert text needs to be sent, not raw credentials.
OpenTelemetry with GrafanaMetrics and traces for the gateway itself (queue depth, processing time, request latency).OpenTelemetry has first-party ASP.NET Core instrumentation.
Kubernetes or Azure Container AppsHorizontal scaling of the API for thousands of nodes. State would first move out of memory into the database.The system is already containerised with Docker Compose, so the same images deploy there.
